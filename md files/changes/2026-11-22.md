## Audit Log page (new)

**Files created**
- `server/src/modules/audit-logs/{types,validation,repository,service,controller,routes}.ts`
- `client/src/types/auditLog.ts`, `client/src/services/auditLogService.ts`
- `client/src/pages/audit-log/{AuditLogPage,AuditLogDetailDialog}.tsx`, `client/src/pages/audit-log/auditLogLabels.ts`

**Files modified**
- `server/src/modules/permissions/catalog.ts` (new `AUDIT_LOG` module: View, Export), `server/prisma/seed.ts` (Super Admin: All, other groups: No Access), `server/src/routes/index.ts` (mounts `/audit-logs`)
- `client/src/types/permission.ts`, `client/src/routes/AppRoutes.tsx` (`/audit-log`), `client/src/layouts/AppLayout.tsx` (sidebar → ADMINISTRATION → Audit Log)

**What / why**
A read-only page over the existing `activity_logs` table that every module already writes to (logins, creates, updates, deletes, payments, order conversions, status changes). Newest first, paginated, with S.No. Columns: When, User, Module, Action, Description, Record. Filters: From / To date, Module, Action, User, and a description search; the Module and Action dropdowns list only values that actually occur in the log. Clicking a row opens a detail dialog with the full description, the structured details (e.g. the from → to of a status change) and, for orders, quotations, enquiries, payment-tracker entries and customers, a button to open the record. CSV export of the current page via the table (needs the Export permission). Dates are sent as the start / end of the user's local day, so "21 Nov" is the user's own day.
Access is its own permission (`AUDIT_LOG`) rather than piggy-backing on another module, because the log names every user's actions. It is read-only: no endpoint edits or deletes entries.

**Database changes**: None (no schema change, so no SQL file).

**API changes**
- `GET /api/v1/audit-logs` — query: `page`, `limit`, `search`, `module`, `action`, `userId`, `dateFrom`, `dateTo` (ISO). Returns `{ id, module, action, referenceId, description, metadata, performedAt, performedBy: { id, fullName, username } | null }[]` with pagination `meta`. Requires `AUDIT_LOG` → `canView`; scoped to the caller's company.
- `GET /api/v1/audit-logs/filters` — `{ modules: string[], actions: string[] }` present in the log. Same permission.

**Follow-up notes**
- **Action needed:** existing groups carry explicit permission rows, so nobody has `AUDIT_LOG` yet. Tick **Audit Log → View** (and **Export**) for Super Admin in Masters → User Groups. Fresh installs get it from the seed. The seed was not re-run: it would also re-add any permission an admin had removed from another group.
- Verified read-only against the dev log (1,373 entries): each filter and combination, newest-first ordering with no overlap between pages, per-company scoping, local-day date ranges, input validation, and the permission gate (denied without the permission, allowed with it; export needs Export). The routes are live and return 401 without a login.
- No index was added: at ~1.4k rows the existing queries are instant. If the log grows large, an index on `(company_id, performed_at)` would be the first thing to add (needs a migration + SQL file).
- Not exercised in a browser (it needs a login).

## Restore for deleted items (Audit Log → Deleted Items)

**Files created**: none (all additions are in existing modules); `client/src/hooks/useConfirmedDelete.tsx` was renamed to `useConfirmedAction.tsx` and generalised.

**Files modified**
- Server: `modules/{enquiries,quotations,orders,payments,expenses,users}/{repository,service,controller,routes}.ts` (a `restore` in each); line endings of the orders and payments files normalised back to their original CRLF.
- Client: `hooks/useConfirmedAction.tsx` (configurable label/tone; `remove` option renamed `action`, `requestDelete` renamed `request`), `hooks/useDeletePayment.tsx`, `pages/audit-log/{DeletedItemsTab,auditLogLabels}.ts(x)`, `pages/orders/{OrderListPage,OrderDetailPage}.tsx`, `pages/orders/tabs/OrderPaymentsTab.tsx`, `pages/payment-tracker/{PaymentHistoryDialog,PaymentTrackerDetailPage}.tsx`, and `services/{enquiry,quotation,order,payment,expense,user}Service.ts` (a `restore(id)` each).

**What / why**
Each row on the Deleted Items tab has a **Restore** button (confirmation first) for every kind listed — enquiries, quotations, orders, payments, expenses and users — shown only to someone who may delete that kind (Users: Masters → Delete). The page refreshes the module's own lists afterwards.
- **A restore brings back exactly what the delete took, and nothing else.** A cascade stamps every record it removes with one instant, so only records carrying the parent's exact deletion time return. Anything deleted on its own earlier — a payment removed by hand, a quotation image removed in the editor — stays deleted.
- **Enquiry** → its quotations, orders, and each order's payments, invoice, payment tracker, task plan and documents. **Order** → its payments, invoice, tracker, task plan, documents and derived quotations. **Quotation** → its images; the enquiry's latest-quotation amount/version is recomputed. **Payment** → the order's paid / pending amounts are recomputed and the tracker status follows. **Expense** and **User** → the record.
- **Refused with a clear message (HTTP 409) when the world has moved on:** an order or quotation whose enquiry is still deleted (restore the enquiry first); an order whose enquiry has since been converted to a different order; a payment whose order is deleted, or one that would take the order's collected amount above its budget; a quotation whose order is deleted; an expense whose category is deleted; a user whose group is deleted.
- Each restore is logged as `RESTORE` (shown in green on the Activity tab); a restored payment also adds a line to its order's timeline.

**Database changes**: None.

**API changes** (all `POST`, no body; `{ success, message, data: null }`; 404 if there is no such deleted record, 409 for the refusals above)
- `/api/v1/enquiries/:id/restore` — `ENQUIRIES → canDelete`
- `/api/v1/quotations/:id/restore` — `QUOTATIONS → canDelete`
- `/api/v1/orders/:id/restore` — `ORDERS → canDelete`
- `/api/v1/payments/:id/restore` — `PAYMENTS → canDelete`
- `/api/v1/expenses/:id/restore` — `EXPENSES → canDelete`
- `/api/v1/users/:id/restore` — `MASTERS → canDelete`

**Follow-up notes**
- No new permission to grant: restoring uses the delete permissions added earlier today.
- Verified against the dev database, always inside rolled-back transactions or with refusals that write nothing (the database was identical afterwards): restoring a really-deleted enquiry returned its order, quotation and a ₹15,000 payment; a quotation image that had been removed nine days earlier stayed deleted while the other six came back; an order deleted and then restored returned its two payments (₹1,00,000), invoice and tracker with the amounts unchanged; a payment deleted and restored took a fully-paid order to Partial Payment and back to Fully Paid; lowering the budget made the restore refuse with the payment left deleted; every 404 / 409 path returned its message; permission gates deny the wrong module; all six endpoints answer 401 without a login.
- The expense and user restores (single-field updates) were verified only through their refusal paths, since the dev data has no deleted user and the one deleted expense would have been restored for real.
- Not exercised in a browser (it needs a login). Restoring rent records is not available because they are not on the Deleted Items tab yet.

**What / why**
Clicking a row on Audit Log → Deleted Items opens a read-only page for that record at `/audit-log/deleted/:type/:id`. It shows: a header (kind, reference, customer / title, amount, a "Deleted" tag, and who deleted it and when — "along with Enquiry ENQ-…" when a parent's deletion took it); the record's fields in labelled sections; its **related records** with an "On restore" column saying which return with it and which stay deleted (deleted separately); and its **history** from the audit log. A **Restore** button (same permission as deleting that kind) restores it and returns to the list; a banner explains what a restore will bring back.
Fields per kind — Enquiry: customer/prospect, event, appointment, quotation & budget, status & assignment; related quotations and orders. Quotation: details, customer, amounts, remarks; related line items. Order: order, customer, money, notes; related payments, invoice, documents. Payment: payment and its order. Expense: details; related receipts. User: profile.
The page is generic (sections / related / history), so one page serves all six kinds.

**Database changes**: None.

**API changes**
- `GET /api/v1/audit-logs/deleted/:type/:id` — `type` one of `ENQUIRIES | QUOTATIONS | ORDERS | PAYMENTS | EXPENSES | USERS`; needs `AUDIT_LOG → canView`; scoped to the caller's company. Returns `{ type, id, reference, title, amount, deletedAt, deletedBy, deletedWith, sections: [{ title, fields: [{ label, value, format, badge? }] }], related: [{ title, items: [{ reference, description, amount, status, badge?, effect }] }], history: [{ id, module, action, description, performedAt, performedBy }] }`. 404 when the record does not exist, belongs to another company, or is not deleted; 400 for a bad type or id.

**Follow-up notes**
- Verified read-only against the dev database for every kind that has deleted data (enquiry, quotation, order, payment, expense): fields, the deleter (including "with Enquiry …" attribution), related records with the right restore effect (e.g. the order's payment is marked "returns"), and history; a live record, a wrong company and a missing id all return not-found; bad type/id are rejected; nothing was written. The user view could not be exercised because there is no deleted user. The route answers 401 without a login.
- A payment's history includes the order's log entries that mention its receipt number, because payments collected through the Payment Tracker are logged against the order rather than the payment.
- Not exercised in a browser (it needs a login).

## Permission changes now reach the signed-in user without a re-login

**Files created**: `client/src/hooks/useProfileSync.ts`
**Files modified**: `client/src/layouts/AppLayout.tsx`, `client/src/pages/masters/tabs/UserGroupsTab.tsx`, `client/src/pages/masters/tabs/UsersTab.tsx`

**What / why**
Report: "payment and orders doesn't have a delete action". The delete actions are only offered to someone who holds the new Orders → Delete / Payment Tracker → Delete Payment permissions, and no group had been granted them (the Super Admin group has no such rows; nor the Audit Log ones), so the buttons were correctly hidden. Separately, a real gap was found: the app saved the signed-in user's profile (including permissions) at login and never re-read it, so a permission granted later stayed invisible until a full sign-out and sign-in. The profile is now re-read from `/auth/me` when the app loads, when the browser tab regains focus (at most every 30 s), and right after a user group or user is saved in Masters. A failed check is ignored, not treated as a sign-out.

**Database changes**: None. **API changes**: None (uses the existing `GET /auth/me`).
