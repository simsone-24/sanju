## Adjust Budget with a mandatory reason (Orders + Payment Tracker)

Real scenario: items are added (or dropped) on the event day, so the order's budget has to change and the change has to be explained.

**Files created**
- `client/src/pages/payment-tracker/AdjustBudgetDialog.tsx` — shared dialog: new budget amount + reason, live "increase/decrease, pending becomes" hint.

**Files modified**
- `server/src/modules/payment-tracker/validation.ts`, `types.ts`, `service.ts` — new `budgetChangeReason`; the service rejects a budget change without it. The budget change is now logged (with from / to / reason) on both the Payment Tracker trail and the order's Timeline (`ORDERS` module), which the Timeline tab reads.
- `client/src/validation/paymentTrackerSchemas.ts` — `adjustBudgetSchema` (reason required, amount > 0, not below collected, must differ from current).
- `client/src/types/paymentTracker.ts` — `budgetChangeReason` on `UpdatePaymentTrackerInput`.
- `client/src/pages/orders/tabs/OrderPaymentsTab.tsx` — "Adjust Budget" button (needs Payments → Edit).
- `client/src/pages/payment-tracker/PaymentTrackerEditDialog.tsx` — "Adjust Budget" button in the summary box (reached from the tracker list and detail page).

**Database changes**
None. The reason is kept in the activity log (as chosen), not a column.

**API changes**
`PUT /api/payment-tracker/:orderId` — new optional body field `budgetChangeReason` (string, max 1000). Required (400) whenever `budgetAmount` differs from the current budget. Budget may go up or down but not below the amount already collected (existing rule).

**Follow-up notes**
- Reasons live only in the activity log, so they can be read per order but not reported on or filtered.
- Older budget-change log entries (before this change) have no reason.

## Phone and WhatsApp numbers optional (Enquiry + Quotation forms)

Both numbers can now be left blank. When a number **is** given it must be valid and unique across customers.

**Files modified (server)**
- `server/prisma/schema.prisma` — `Customer.mobile` is now optional.
- `server/src/modules/customers/` (`service.ts`, `repository.ts`, `validation.ts`, `types.ts`) — one shared uniqueness check for mobile **and** WhatsApp (409 naming the existing customer); `null` clears a number.
- `server/src/modules/enquiries/` (`validation.ts`, `service.ts`, `types.ts`) — mobile no longer required for a new customer (still validated when given); converting an enquiry to a customer no longer needs a mobile, and matches an existing customer by mobile, then WhatsApp; the enquiry API still returns `customer.mobile` as a string (`''` when blank).
- `server/src/modules/quotations/` (`validation.ts`, `repository.ts`) — manual quotation WhatsApp is optional; editing a manual quotation can now clear phone / WhatsApp.
- `server/src/modules/invoices/` (`pdf.ts`, `types.ts`) — invoice "Bill To" skips a missing mobile.

**Files modified (client)**
- `validation/enquirySchemas.ts`, `validation/quotationSchemas.ts`; `pages/enquiries/EnquiryFormPage.tsx`, `CustomerEditDialog.tsx`; `pages/quotations/QuotationFormPage.tsx` — fields no longer marked required / validated as required; clearing a number sends `null`.
- Types (`customer`, `order`, `paymentTracker`, `report`, `invoice`, `masters`, `enquiry`, `quotation`) and display spots (customer list export, WhatsApp buttons on Order / Order quotation / Invoice, dropdown labels) made null-safe.

**Database changes**
`database/2026-11-17/01_make_customer_mobile_optional.sql` (migration `20261117000000_make_customer_mobile_optional`, applied).

**API changes**
`PATCH/PUT` customer and enquiry updates accept `mobile: null` / `whatsapp: null` to clear. Customer create/update returns 409 if a given mobile **or** WhatsApp number already belongs to another customer. Manual quotation `manualCustomer.whatsapp` is optional.

**Follow-up notes**
- Uniqueness is checked in the service layer (as it already was for mobile), not by a database unique index.
- It applies to customer records. Enquiry prospects and manual-quotation snapshots are not customers, so they are not checked against each other; a prospect's number is matched to an existing customer when the enquiry is confirmed.
- A quotation with no WhatsApp/phone number can't be shared on WhatsApp (the share button stays unavailable).

## Existing customer's number can't start a new enquiry customer

**Files modified**
- `server/src/modules/enquiries/service.ts` — `assertProspectNumbersFree`: creating an enquiry with a NEW customer, or changing a prospect's phone / WhatsApp, is rejected (409, names the existing customer) when that number already belongs to a customer. On edit only a number being changed is checked.
- `server/src/modules/customers/repository.ts` — customer search also matches WhatsApp numbers.
- `client/src/pages/enquiries/EnquiryFormPage.tsx` — on a new enquiry, typing a full 10-digit phone / WhatsApp number looks the customer up; on a match the form switches to **Existing Customer**, selects that customer (details load into the card) and clears the typed name/numbers, with an info toast.
- `client/src/types/masters.ts` — `CustomerOption.whatsapp`.

**Database changes**
None.

**API changes**
`POST /api/enquiries` and `PUT /api/enquiries/:id` return 409 `Customer "<name>" already exists with this phone number / WhatsApp number. Select the existing customer instead…` (field `mobile` or `whatsapp`).

**Follow-up notes**
- The automatic lookup needs Customers → View; without it the user simply gets the 409 message on save.
- Only exact matches on the same field are checked (a customer's mobile against the typed mobile, WhatsApp against WhatsApp). Two unconfirmed enquiries can still share a number.
