**Files created**

- `client/src/services/expenseService.ts`, `client/src/types/expense.ts`, `client/src/validation/expenseSchemas.ts`

**Files modified**
- `server/prisma/schema.prisma` — `ExpenseCategory`, `Expense` models, `ExpenseCategoryStatus` enum, back-relations
- `server/prisma/seed.ts` — `EXPENSES` row in the permission matrix
- `server/src/modules/permissions/catalog.ts` — new `EXPENSES` module (View, Create, Edit, Delete, Export)
- `server/src/routes/index.ts` — mounts `/expenses` and `/expense-categories`
- `client/src/types/permission.ts`, `constants/routes.ts`, `routes/AppRoutes.tsx`, `layouts/AppLayout.tsx` — module type, routes, sidebar item (Management section)

**What changed and why**
Standalone expense ledger (not linked to orders): category, date, amount, payment method (existing fixed `PaymentMethod` enum), paid to, description, optional receipt (JPG/PNG/WebP/PDF, 5MB, served only through an authenticated, company-scoped endpoint). Categories are a company master managed under the Expenses permissions. Soft delete; create/update/delete/category status changes are written to the activity log. A category with expenses cannot be deleted (mark inactive instead); inactive categories cannot be chosen for new expenses.

**Database changes**
New tables `expense_categories`, `expenses` — see `database/2026-11-16/01_create_expenses.sql` (matches the Prisma migration; verified with `prisma migrate diff`).

**API changes**
- `GET /expenses` — filters: `search`, `categoryId`, `paymentMethod`, `dateFrom`, `dateTo`, `page`, `limit`
- `GET /expenses/:id`, `DELETE /expenses/:id`
- `POST /expenses`, `PUT /expenses/:id` — multipart/form-data: `categoryId`, `expenseDate`, `amount`, `paymentMethod`, `paidTo?`, `description?`, `receipt?` (file). On PUT an empty `paidTo`/`description` clears it; a new `receipt` replaces the old file.
- `GET /expenses/:id/receipt` — receipt download
- `GET|POST /expense-categories`, `GET|PUT|DELETE /expense-categories/:id` — JSON `{ name }` / `{ name?, status? }`
- All use the standard success/error envelope; every route requires the `EXPENSES` permission.

**Follow-up notes / known limitations**
- Migration has to be applied (`npx prisma migrate dev` / `migrate deploy`) and existing user groups granted the new Expenses permissions in Masters (the seed only sets them for a fresh install).
- Table sorting is client-side over the current page, like every other list in the app.
- No receipt removal without replacement, and no approval workflow or summary report (not requested).

## Expenses — popup form and category entry from the expense form

**Files modified**
- `client/src/pages/expenses/ExpenseListPage.tsx`, `ExpenseCategoryListPage.tsx` — add/edit forms now use the existing `FormDialog` (centered modal) instead of `FormDrawer`
- `client/src/pages/expenses/ExpenseListPage.tsx`, `types/expense.ts`, `services/expenseService.ts`, `validation/expenseSchemas.ts` — Category is a type-or-pick field that sends `categoryName`
- `server/src/modules/expenses/{validation,types,service}.ts` — create/update accept `categoryId` or `categoryName`
- `server/src/modules/expense-categories/repository.ts` — name lookup also returns name and status

**What changed and why**
A name typed in the expense form is matched against the category master (case-insensitive, via the column collation) and reused if it exists; otherwise the category is created in the master through the category service (logged as a category CREATE). The master never gets a duplicate, including under concurrent requests (the 409 is handled by re-reading). A name matching an inactive category is rejected unless the expense already uses it.

**Database changes**
None.

**API changes**
`POST /expenses` and `PUT /expenses/:id` accept `categoryName` (new or existing) as an alternative to `categoryId`; sending both is rejected, and create requires exactly one.

**Follow-up notes**
Creating a category this way needs the Expenses Create permission, same as the category master.

## Expenses — multiple receipts (images / PDFs) per expense

**Files created**
- `server/prisma/migrations/20261116000100_expense_multiple_receipts/migration.sql`
- `database/2026-11-16/02_expense_multiple_receipts.sql`

**Files modified**

- `server/src/modules/expenses/{types,validation,repository,service,controller,routes,receipt}.ts`
- `client/src/types/expense.ts`, `services/expenseService.ts`, `pages/expenses/ExpenseListPage.tsx`

**What changed and why**
An expense can now carry up to 10 receipts (JPG, PNG, WebP or PDF, 5MB each). The form shows attached receipts as chips (click to download, × to detach) and a multi-file picker for new ones; the list's paperclip shows the count and opens a menu to download each. Adds and detaches are saved together with the expense in one transaction; detached files are deleted from disk after the save. Existing single receipts are copied into the new table by the migration.

**Database changes**
New table `expense_receipts`; `expenses.receipt_file_name` and `expenses.receipt_path` dropped after their data is copied across — see `database/2026-11-16/02_expense_multiple_receipts.sql`.

**API changes**
- `POST /expenses`, `PUT /expenses/:id` — multipart field `receipts` (repeatable, max 10) replaces `receipt`. `PUT` also accepts repeatable `removeReceiptIds`.
- `GET /expenses/:id/receipts/:receiptId` replaces `GET /expenses/:id/receipt`.
- Expense responses carry `receipts: [{ id, fileName }]` instead of `hasReceipt` / `receiptFileName`.

**Follow-up notes**
- The migration must be applied before the new server code runs.
- The rollback keeps only the first receipt of each expense.
